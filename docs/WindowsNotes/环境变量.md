## PATH 变量
Windows 搜索命令的逻辑与 Linux 类似，都依赖 `PATH` 变量，但 Windows 多了一步**文件扩展名**的解析，并且把**当前目录**放在了优先搜索的位置。

### 🔍 Windows 的具体搜索顺序

当你直接在命令行输入一个不带路径的命令（如 `tasklist`）时，搜索流程大致如下：

1.  **内部命令**：首先检查是否为 `cd`、`dir` 这类内置命令，是则直接执行。
2.  **当前目录**：接着在当前工作目录中查找。它会依次尝试 `命令名.扩展名` 的组合。
3.  **PATH 环境变量**：如果当前目录找不到，就会按顺序遍历 `PATH` 变量里列出的文件夹。
4.  **扩展名匹配**：在以上**每一个**步骤的目录中，如果没指定扩展名，Windows 会按 `PATHEXT` 变量里定义的顺序（通常是 `.com`, `.exe`, `.bat`, `.cmd` 等）去尝试匹配。找到**第一个**匹配的文件即停止搜索并执行。

Windows 在构建进程的 `PATH` 时，逻辑是**系统级优先，用户级追加在后**。也就是说，最终生效的 `PATH` 列表里，系统路径会排在用户路径的前面，更优先的位置。

### PATH 变量的特殊性
Windows 对 `PATH` 的处理和其他环境变量是**两套逻辑**。

#### 📌 普通环境变量：用户级完全覆盖系统级
对于 `TEMP`、`USERNAME` 这类普通变量，如果同名，**用户级设置会直接替换掉系统级的值**。

#### 📌 PATH 变量：用户级是“追加”而非“覆盖”
`PATH` 是一个特例。系统构建最终 `PATH` 时，顺序是 **`系统PATH;用户PATH`**。
这意味着：
*   **系统路径排在前面**，搜索命令时会被优先命中。
*   **用户路径排在后面**，起到“补充”和“扩展”的作用，而不是“覆盖”。

#### 🎯 为什么 PATH 要这样设计？
这主要是出于**系统安全性和稳定性**的考量。如果用户级 `PATH` 能轻易覆盖系统路径，恶意软件就可能通过用户变量劫持系统命令（比如替换掉 `ping`、`dir`），或者用户误操作导致系统核心命令找不到，影响系统稳定。

所以，在 Windows 上，如果你想用自己安装的某个版本去“覆盖”系统里已有的命令，单纯把它加进用户级 `PATH` 通常是不够的，因为它可能排在系统路径后面，永远轮不到它被执行。
